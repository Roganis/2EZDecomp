# Port work queue — what to reconstruct next, and why

Generated by `scratchpad/spine.py`. **Regenerate it** after any batch of work:

    .venv/bin/python scratchpad/spine.py 40

The ranking is *reachability from the application entry points*, not branch
density. `scratchpad/scan.py` (branch density) answers "what is cheapest to
match"; this file answers "what does a running game actually need". They
disagree often — prefer this one while the goal is a port.

**Regenerated 2026-08-23, after fixing three boundary bugs in `spine.py` that
made every previous version of this file wrong.** It treated every `jmp rel32`
target as a function start, so each loop tail and `else` inside an already
reconstructed function counted as a separate unreconstructed one; and the walk
put addresses that are not function starts into the reached set, where they
had no size and no annotation. Together those reported *988 unreconstructed
spine functions and 154 KB* when the real figures are **74 and 73 KB**, and
they understated the spine itself by a third. If you have planned off an older
copy of this file, re-read it.

**The three constructors are the cheap end**, which is the opposite of how they

member-ctor calls, `loadTexture`/`loadStr` with literal paths, and blocks of
field defaults. The tick functions at the bottom are where the real branching
logic is.

**AND SCREEN FOR FLOAT MATH AND MODE LADDERS BEFORE COMMITTING A TICK:
`scratchpad/screen.py LO SIZE`.** Both ranking metrics below predict
TRANSCRIPTION cost; what actually costs time is READING, and two things drive
that. A run of `movss`/`comiss`/`cvtsi2ss` has to be read expression by
expression, and a mode ladder (runs of cmp/je against one register, each arm
calling something different) has to be read arm by arm. Between them they
mis-sized three targets in a row - 0x42a630 at a comfortable 0.090
branches/insn is the hold-note renderer's geometry, 0x45bc30 at 0.106
calls/insn is a float score count-up, and 0x4249e0 at the very top of the
calls ranking is a lamp-routing ladder. The screen flags all three and passes
the four that were written first try at 73-91%.

**RANK BY CALLS PER INSTRUCTION, NOT BRANCH DENSITY.** Branch density says
how tangled a function is; calls-per-instruction says whether it is a TABLE
(mechanical, fast to write) or COMPUTATION (dense, slow). They disagree, and
the branch-density ranking above sent me at `0x42a630` - 2,304 bytes and a
comfortable 0.090 branches/insn, but only 27 calls in 687 instructions, which
makes it the hold-note renderer's float geometry rather than a table of loads.

Above ~0.10 is mechanical; below ~0.06 is dense arithmetic that has to be
read line by line. Combine the two: want high calls/insn AND a small byte
count for timed work.

**TICK-SIZED VS SESSION-SIZED, measured 2026-08-25.** The loop writes these on
~25-minute ticks and that is the wrong unit for the top of this list.
`0x44e9b0` (2,352 bytes, 71 calls, 20 branches) fitted: one tick to prepare,
one to write, 81%. `0x4682e0` (5,776 bytes, **196 calls, 98 branches**) does
not, and the branches are why - its asset loads are mode-conditional (BG.str
against coursebg.str against bg_GameOver.str; CatchResult / Result / Battle
panels; 1p and 2p songrank variants), so the table assetmap.py produces has to
be read back against the listing to recover which arm each load sits in. That
is a sitting, not a tick.

Its texture set IS carved and named (include/directors.h, from the asset map),
which is the durable half of the value and is done. What remains is the body.

For tick-sized port work prefer the middle of this list - `0x42a630` (2,304
bytes, 0.090 br/insn), `0x459bc0` (1,744, 0.124), `0x4249e0` (1,856) - and
leave the two giant constructors for a run that is not on a timer.

Start with `0x44e9b0`. It is decoded already - the full section-by-section
reading is in its stub comment in `src/stubs.cpp`, including the asset-to-chart
map and the version-readout digit split - so it is a transcription job, not an
analysis one.

## Do these first regardless of the list

* **Read `docs/PORT-DELTAS.md`.** Findings from the decomp that the port's own
  code contradicts or does not implement — the keys hold ladder (which is *not*
  the catch one the port implements), the instalment count's −1, the pump's

  functions.

* **Read `wip/` before reconstructing anything.** 37 functions are decoded and
  merely un-*matched*; for a port they are complete. `wip/README.md` opens with
  the audit that keeps that list honest — six parks were found describing work
  already finished in `src/`.

* **The biggest single win is the song-select mode-input family.** Nine
  functions, ~25 KB, and they are the top of the unreconstructed list below:
  `0x43ad10`, `0x43c2e0`, `0x43cf30`, `0x43dc00`, `0x43e8d0`, `0x43f390`,
  `0x440af0`, `0x441540`, `0x442770`. They are **walled for matching** (the
  constant-register assignment documented in CLAUDE.md — do not try to match
  them) but they are 73–78% similar to `0x43ff00` and `0x43b8d0`, which ARE
  matched and readable in `src/songselectinput.cpp`. For a port they are
  copy-and-edit from a working template, not fresh analysis. Nothing blocks
  this work.

  **Sized 2026-08-23 with `scratchpad/twindelta.py`, which is what makes this
  tractable.** Diffing two siblings raw is useless - they sit at different
  addresses so every branch target differs, and cl resolves the
  constant-register coin differently in each, so `push $0x1` against
  `push %ebp` shows up dozens of times. The tool masks in three passes and
  reports only what survives folding the coin away. Every one of the nine is
  closest to `0x43ff00` (5KeyMix), and the edit distance is very uneven, so
  work them in this order:

  five written this session barely moved them - they are the family's second
  shape. But they are **0.84-0.94 similar to EACH OTHER**, so the order that
  matters is: write ONE properly, and the other three become edits of it.
  By average similarity to the other three the hub is `0x43f390` (0.914),
  then `0x43dc00` (0.910); `0x43e8d0` is the worst choice (0.879).

  Budget the hub as a real decode, not an edit: 779 instructions, ~100 more
  than any template, and it calls `InGameSongSelect::pickDistinct` @0x433cf0
  FIVE times plus `0x414e30` twice - a course-picking mechanic none of the
  first six have. `0x441fa0` (CV2Mix) is the odd one out at 0.544 against
  everything and should be left until last.

  Two levers found while doing them, both worth trying on the remaining five:
  the first-page lamp block wants `int c` declared before `int b` (worth
  0.5-1.5 points on every handler that has the fourth option), and a frame
  that comes out four bytes larger than the template's is the constant-register
  coin showing up as a frame size, not something the source has to say - cl
  reproduced SpaceMix's by itself.

  The deltas that show up are what a port has to get right: an extra option
  counter, a different wrap limit, one comparison changed from `!=` to `<`.
  The first three are a few dozen lines of edit each on a 335-line template.

  **Three done, 2026-08-23** (`src/songselectinput.cpp`), and the method holds:
  read the semantic deltas, copy the template body, apply four or five edits,
  build. All three landed first build at 93.4% / 93.5% / 98.7% - above the template's
  own 88.39% - and ScratchMix then went to a BYTE-EXACT 100% on one edit (the
  lamp block's `int b` and `int c` declared in the wrong order). Each took
  about twenty minutes. That also retires the assumption that this family is
  uniformly walled: the wall is 5KeyMix and EZ2Catch specifically, so write
  the next one before deciding it is hopeless. Expect the four at 0.57-0.60 to be
  several times that: their region counts are three times higher and they are
  the second shape in the family, so 0x43ff00 may not be the right template
  for them at all - re-run twindelta against 0x43cf30 once one of THEM is
  written.
