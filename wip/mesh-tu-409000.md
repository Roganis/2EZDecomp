# The 0x409330–0x40a46c static cluster — ONE TU, and it WORKS (2026-08-18)

**src/kgraphicsworm.cpp.** The whole cluster is written as one translation
unit and cl gives every `static` helper the ORIGINAL's register convention
from plain source (t in xmm2 for evalSpline / xmm1 for evalCurve, the mesh in
ebx / ecx / edx, vectors in eax / ecx / edx / esi / edi, the out-pointer of
evalSpline in eax and returned). The register-convention risk recorded below
did not materialise; what decides the convention is the callee's own body.

What was load-bearing (all in the source comments too):
* loop counters are `unsigned short` (that is what keeps the four-point
  accumulate loop a loop, and the WORD `movzx` everywhere);
* the Catmull-Rom weights are NAMED TERMS (`a = -1.0f * t3; ...`) - written
  inline cl folds `-1*x + y` into a subtract; the original multiplies by -1.0;
* evalSpline returns its out-pointer (`GVec3 *f(t, out, cp)`), which is what
  lets the caller read the second result straight out of the temp;
* the view matrix is its own global (0xd49df8) so `push &view` is at an
  entity base; reccmp patch 14 names `push &g_worm.member` for the two
  interior pushes createWorm makes;
* array `new` needs `operator new[]` DECLARED (kcrt.h) to reach the
  out-of-line `jmp malloc` @0x47854c (src/newarray.cpp), else cl uses the

Mapped 2026-08-18 while looking at 0x409330. CLAUDE.md's warning names only
"the 0x409660 / 0x409a30 cluster"; it is bigger than that and it has a shape.

## What it is

A mesh/geometry builder compiled as a single translation unit: two public
entry points, a set of `static` helpers with cl-assigned register conventions,
and a block of file-scope statics they all share.

**Entry points** — called normally from outside, so these are ordinary
methods:

| addr | called from | convention |
| --- | --- | --- |
| 0x409d90 | @0x45c66c, @0x46ad9c (two directors, via `g_sub1b2f054`) | `__thiscall` on KGraphics |
| ~0x40a0xx | (the function containing @0x40a0ba/0x40a11a/0x40a384/0x40a392) | same family |

**Statics** — every one of these takes at least one argument in a register no
documented convention would use:

| addr | how the caller sets it up |
| --- | --- |
| 0x409330 | `mov ecx,0xd49cb8` + THREE `__cdecl` stack args; the callee `ret`s without cleaning and the caller does `add esp,0xc` |
| 0x409660 | `mov esi,0xd49cf0` / `mov edx,0xd49cb8` / a float in `[esp]` |
| 0x409830 | `mov edx,edi` / `mov ecx,esi` |
| 0x409a30 | `mov edi,0xd49d08` / `mov esi,0xd49cfc` / `mov ecx,0xd49cb8` |
| 0x4094f0 | `movss xmm2,...` / `lea edx,[esp+0x1c]` |
| 0x409ce0 | calls 0x409660 and 0x409a30; itself zero-branch |
| 0x409980 | five floats in xmm0..xmm4, an out-pointer in eax, two stack args, cleans 0x1c itself |

**The shared statics** live at 0xd49cb8, 0xd49cc0, 0xd49cf0, 0xd49cfc,
0xd49d08 and 0xd49dcc — file-scope data, which is the other half of the
one-TU evidence.

## Why it cannot be picked at

cl gives a `static` that is not address-taken its own register convention,
chosen per-TU from what the whole TU needs. So none of these can match while
it is declared normally, and reconstructing one without its callers cannot
work however the body is written. The unit is roughly 4.6 KB across nine or
ten functions, and it either matches together or not at all.

## What 0x409330 does, since it was read

Build the index buffer for a grid: `[ecx+0x110]` is the row count, the three
stack args are a base pointer and two 16-bit scale factors, and the loop
writes six `WORD`s per step - two triangles - advancing two output pointers at
once. Sixteen-bit arithmetic throughout (`imul ax,WORD PTR [esp+0x18]`), with
the 32-bit `idiv [ecx+0x110]` giving the row/column split.

## Recommendation

A dedicated session, bottom-up: write all the statics and both entry points in
one .cpp, build once, and expect to iterate on the register assignment as a
whole rather than per function. Not tick-sized, and not worth starting until
someone can hold the whole TU at once.
